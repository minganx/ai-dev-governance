# 全局开发规则

> 本文件是 AI 开发工具共享的通用规则源文件。项目级规则优先于本文件。

## 响应原则

1. 简洁干练，不啰嗦。
2. 不确定时先澄清，不基于猜测行动。
3. 不用 fallback 掩盖问题；定位并解决根因。
4. 输出必须可执行、可验证、可落地。

## 开发原则

1. 精益开发：只构建当前明确需要的能力。
2. 渐进式开发：每一步都是可验证的完整切片。
3. Rule of Three：至少出现三个具体实现后再抽象。
4. PEP 20：显式优于隐式，可读性优先。
5. Clean Code：所有改动以长期可维护性为前提。

## 编码规范

- 遵循项目指定的语言版本、命名和格式规范。
- 禁止添加无业务依据的 default、fallback、兼容分支和未使用参数。
- 代码优先清晰表达业务意图。
- Python 项目使用项目指定的依赖管理器；项目使用 uv 时禁止 `uv pip`。

## Git 工作流

- 使用 `<类型前缀>/<简短描述>` 功能分支；主分支和既有版本干线除外。
- 子分支默认通过 Squash merge 合入主分支或版本干线。
- Commit 使用 Conventional Commits。
- 每个 Commit 只做一类改动。
- 提交前审查工作区、暂存区和变更范围。
- 禁止用 `--no-verify` 绕过 Hook。

### Commit 正文

- Commit 必须包含有效正文。
- 正文应清楚覆盖问题现象、分析原因、修改内容和修改后结果。
- 表达形式和顺序不限，不强制固定标签。
- 不得只罗列文件名、使用占位符或填写“更新代码”“修复问题”等无效描述。
- 未执行的验证不得写成已完成结果。

## 文档治理

- 中文项目文档统一使用中文，保留必要英文专有名词。
- 文档陈述事实，避免教学语气。
- 文档内容必须与代码、配置和运行行为一致。
- 文档以产品目标或工程目标为归属，不以分支或完成状态作为稳定目录。
- 路线图按产品演进阶段表达顺序、目标、需求、状态和资料链接，不用优先级清单替代路线图。
- 需求记录保持轻量；除非项目明确要求，不在仓库内建设完整需求管理系统。
- 已完成资料保持稳定路径；归档区只保存已失效、被替代或已取消的资料。
- 描述当前系统事实的架构、接口和运维文档保持独立，并由相关目标更新。

## 代码质量门禁

- 完成修改前执行项目定义的最终质量门禁。
- 配置了 pre-commit 的项目必须完整跑通。
- 检查命令和工具链以项目规则为准，不假设具体语言或命令存在。
- 行为变化必须执行与风险相匹配的验证。
- 检查未通过或验证未执行时不得声称完成。

## 资料检索

- 用户询问库、框架、SDK、API、CLI 或云服务时，优先使用 Context7 查询当前官方文档。
- 先解析准确的库标识，再按单一概念查询；跨多个概念时分别查询。
- 代码审查、业务逻辑调试、通用编程概念和无第三方依赖的脚本不触发 Context7。

## AI 工具治理

- 项目根目录规则是项目事实来源，各工具入口只做薄转发。
- 通用 Skill 提供跨项目基线；项目 Skill 只添加项目差异，并使用不同名称避免覆盖全局 Skill。
- 强制质量规则落在仓库配置、共享脚本和 Git Hook 中，不依赖单一 AI 工具的私有 Hook。
- 工具专属配置只负责发现、加载和交互适配，不复制项目规则正文。

## Agent 行为

- 小范围修改：直接定位、修改、验证。
- 中等以上修改：先说明方案，再实施。
- 涉及架构、数据库、接口、迁移或交付兼容时，先明确规格和影响范围。
- 保留用户已有改动，未经授权不覆盖、不删除、不改写历史。
