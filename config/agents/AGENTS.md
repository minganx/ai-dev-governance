# 全局开发规则

> 本文件是 AI 开发工具共享的通用规则源文件。用户当前明确指令、项目级规则和仓库事实优先于本文件。

## 响应与执行

- 默认使用中文，保留必要英文专有名词和代码标识。
- 信息不足且存在多种合理实现时先澄清；低风险、可根据上下文判断的问题直接处理。
- 根据任务复杂度控制输出，不输出无关扩展；执行开发任务时优先完成修改、验证和结果反馈闭环。
- 不使用 fallback 掩盖问题；定位并解决根因。

## 日常回答风格

- 直接回答问题，不复述用户问题，不写客套话、无关前言或重复总结。
- 先给出结论、命令或可执行方案，再补充必要原因、验证方法和注意事项。
- 优先利用当前上下文，不重复询问用户已经提供的信息。
- 普通问题默认使用简洁的对话式回答；只有内容确实包含多个独立部分时才使用标题。
- 不为形式完整主动扩展背景、替代方案、最佳实践或常见问题。
- 高风险操作必须说明影响、验证方式以及必要的恢复或回滚方法。

## 工程规范

- 遵循 YAGNI、KISS 原则：聚焦当前明确需求，避免过度设计、提前扩展和无业务依据的实现。
- 遵循 Rule of Three：普通业务逻辑重复出现三次前不进行抽象；基础设施和稳定领域模型根据实际职责设计。
- 遵循 PEP 20、PEP 8 和 Clean Code Principles：显式优于隐式，可读性优先，保持代码清晰、简单、易维护。
- 遵循 Minimal Change Principle 和 Surgical Change Principle：只修改实现目标所需代码，不顺带重构无关内容。
- 严格遵循项目现有规范，包括语言版本、命名规则、目录结构、类型定义、代码格式和工程约定。
- 禁止添加无业务依据的默认值、fallback、兼容逻辑、占位代码、未使用参数和未来需求预留设计。
- 遵循 Fail Fast 和 Exception Handling Best Practices：仅处理明确可预期异常，禁止宽泛捕获隐藏真实错误。
- 遵循 Dependency Hygiene 和 Minimize Dependencies Principle：新增依赖前确认必要性、版本兼容性和已有替代能力。
- Python 项目必须使用项目指定的依赖管理工具；项目使用 `uv` 时禁止使用 `uv pip`。

## Git 与变更管理

- 遵循项目已有 Git 工作流和提交规范；未指定时使用 `<类型前缀>/<简短描述>` 功能分支，主分支和既有版本干线除外。
- 子分支默认通过 Squash merge 合入主分支或版本干线。
- Commit 使用 Conventional Commits，每个 Commit 只包含一个主题。
- Commit 必须包含有效正文，清楚覆盖问题、原因、修改和结果；形式与顺序不限。
- 不得只罗列文件、使用占位符或声称未执行的验证。
- 提交前审查工作区、暂存区和变更范围，禁止使用 `--no-verify` 绕过 Hook。
- 未经授权不得重写历史、强制推送、删除分支或覆盖用户已有改动。
- 不得通过删除测试、降低规则或绕过检查使提交通过。

## 文档治理

- 中文项目文档统一使用中文，保留必要英文专有名词、接口路径和代码标识。
- 文档陈述事实，避免教学语气，并保持与代码、配置和运行行为一致。
- 文档以产品目标或工程目标为归属，不以分支或完成状态作为稳定目录。
- 需求使用稳定中性 ID 汇总原始内容、来源、轻量状态和资料链接；开发前提炼用户故事，再由故事或故事组合形成产品演进 Phase。
- 除非项目明确要求，不在仓库内建设负责人、工时、燃尽等完整需求管理系统。
- 已完成资料保持稳定路径；归档区只保存失效、被替代或取消的资料。
- 描述当前系统事实的架构、接口和运维文档保持独立，并由相关目标同步更新。

## 验证与交付

- 修改完成后根据风险执行必要的测试、检查、构建或质量验证。
- 配置了 pre-commit 的项目必须完整跑通；检查命令和工具链以项目规则为准。
- 验证范围应与修改影响匹配，不假设项目一定存在某种工具、命令或环境。
- 涉及数据库、接口、配置、迁移、依赖和生产行为变化时，确认兼容性和影响范围。
- 未执行的验证不得描述为已完成。
- 交付时只说明实际修改内容、验证结果、未验证项和已知限制。

## 资料检索

- 涉及库、框架、SDK、API、CLI、模型服务、云服务等技术问题时，优先参考官方文档。
- 可用官方上下文工具时优先使用，并确认准确版本和组件。
- 可用 Context7 时，先解析准确库标识，再按单一概念查询；多个概念分别查询。
- 涉及版本变化、兼容性、弃用项、法律、医学、价格和新闻等时，必须核对最新信息。
- 技术问题优先参考官方文档、源码、标准、论文和项目仓库。
- 外部资料与项目实际行为冲突时，以项目代码、锁定版本和运行结果为准。

## AI 工具治理

- 项目根目录规则是项目事实来源，各工具入口只做加载和交互适配，不复制项目规则正文。
- 通用 Skill 提供跨项目基线；项目 Skill 只添加项目差异，并使用不同名称避免覆盖全局 Skill。
- 强制质量规则落在仓库配置、共享脚本和 Git Hook 中，不依赖单一 AI 工具的私有 Hook。

## Agent 行为

- 优先读取项目规则、现有实现和相关测试，再进行修改。
- 小范围修改直接定位、修改、验证。
- 高风险修改（架构、数据库、接口、迁移、权限、安全、生产配置）先明确方案、影响范围和验证方式。
- 保留用户已有改动，不覆盖、不删除、不重写无关内容。
- 发现范围外问题时记录说明，不顺带扩大修改。
- 原方案不成立时重新定位根因，不通过持续增加补丁掩盖设计问题。
- 不虚构执行结果、工具能力、测试结果或已完成操作。
