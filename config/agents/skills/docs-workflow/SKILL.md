# 文档工作流

项目 `AGENTS.md` 和项目增量 Skill 优先于本通用基线。

## 基本规则

- 修改前核对代码、配置、Git 变更和现有文档。
- 中文项目文档使用中文，保留必要英文专有名词和代码标识。
- 文档陈述事实，避免教学语气。
- 存在版本号的文档维护修订记录。
- 接口、配置、迁移和运行说明必须与当前实现一致。

## 技术笔记

仅在用户明确要求整理笔记、形成文档、输出手册或汇总落档时启用：

- 只输出笔记正文，不添加客套话、过程说明或重复总结。
- 一篇笔记只处理一个明确主题，不混合部署、调优、排障和架构设计。
- 标题最多三级；减少碎片列表，参数密集信息优先使用表格。
- 代码块必须标注语言；命令完整可执行，参数说明放在代码块外。
- 终端输出使用 `text` 代码块；未经验证的结果明确标注为“预期”。
- 部署和排障笔记包含必要的执行、验证、日志、停止、恢复、回滚或删除步骤。

## 目标导向模型

项目采用路线图和目标专项体系时：

- 需求池是所有需求来源的统一入口；每条需求使用不编码优先级、类型、Phase 或状态的稳定中性 ID。
- 一句话需求直接记录；存在背景、风险、目标或方案时链接详细资料，不能因描述简单而拒绝收录。
- 开发前从一个或多个需求提炼用户故事；一个需求可以拆分为多个故事，多个需求也可以组合成一个故事。
- 路线图按产品演进 Phase 记录顺序、目标、用户故事、来源需求、状态、专项和资料链接。
- Phase 是用户故事或故事组合形成的产品演进阶段，不是需求录入时的初始分类。
- 专项是围绕同一交付目标组织的一组需求与资料；专项路径不绑定分支、Phase、类型或完成状态。
- 需求和用户故事状态只标记是否完成或关闭，不扩展为完整需求管理系统。
- SDD、DDD、验证和验收资料归属于专项。
- 已完成专项保持原路径；归档区只保存失效、被替代或已取消的资料。
- 当前有效的架构、接口和运维文档保持独立，由相关专项同步更新。

## 文档阶段

| 阶段 | 内容                                     |
| ---- | ---------------------------------------- |
| SDD  | 目标、范围、契约、状态语义和验收标准     |
| DDD  | 纵向最小可运行切片、依赖、任务和验证方式 |
| 验证 | 实现记录、命令、真实链路和结果           |
| 验收 | 验收范围、证据、遗留边界和结论           |

- 信息不足时只澄清，不设计、不编码。
- 任务拆分使用确定性表述，不保留“建议、可选、待定”。
- 每个切片必须可独立运行和验收。

## 文档审查

发布或高影响合并前，按项目实际范围覆盖：

| 角色       | 检查重点                       |
| ---------- | ------------------------------ |
| 对接工程师 | 接口路径、参数、响应和状态契约 |
| 运维人员   | 配置、迁移、部署、升级和排障   |
| 接手工程师 | 当前架构、模块关系和关键约束   |
| 交付工程师 | 构建、交付物、初始化和升级链路 |
| 架构师     | 路线图、专项、架构和索引一致性 |

输出问题时使用：

```text
| 严重度 | 文件 | 行号 | 问题描述 | 代码实际行为 |
```

修复后重新审查；未纳入当前范围的长期项登记到项目路线图或需求池。
