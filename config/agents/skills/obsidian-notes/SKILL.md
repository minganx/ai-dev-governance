# Obsidian 笔记规范

仅在用户明确要求整理、迁移、更新 Obsidian 笔记或编写实践手册时使用。

## 目录与归类

- `inbox/`：尚未消化的材料。
- `work/`：按公司、项目组织的工作资料。
- `knowledge/`：按系统运维、数据库、网络等领域组织的知识。
- `notes/`：私人资料；不得把 Token、密钥或隐私内容迁入公开仓库。
- `knowledge/` 按知识领域分目录，如 `系统运维/Linux/`、`系统运维/网络/`；不按发行版、机器或项目分目录。发行版差异写成笔记内章节，如「Ubuntu 操作」。
- 一个知识领域一份笔记，工具和知识点使用二级标题分章；内容过长或明显难读时在领域目录内拆分。
- 实践手册放在对应领域的 `实践/` 子目录；属于具体项目的部署手册放在 `work/<公司>/<项目>/`。
- 拆分合集时，知识内容并入领域笔记，实践内容单独成文，拆分后删除原合集。
- 新材料先进入对应目录；`inbox/` 内容消化后迁出。

## 笔记类型

动笔前先判断类型。「通用规则」适用于所有笔记；「知识笔记」「实践手册」两章只适用于各自类型，互不套用。

- **知识笔记**：回看原理、复习方法，解释“是什么、为什么、如何工作”。
- **实践手册**：用户照着执行的资料，不是教学课本。包括部署手册（按步骤执行）和案例记录（某台机器的现象与处置）。

## 通用规则

### 内容

- 只记录当前有效的事实、配置、命令、参数和行为边界。
- 推测、验证计划和方案对比不写成稳定笔记事实。
- 迁移或重整旧文时逐项对照主题、关键解释、例子和代码，保留有效内容；解释性内容归入知识笔记，操作和案例归入实践手册。不因压缩或表格化丢失信息。重复内容可合并，错误或过时说明核实后修正；交付前再次检查覆盖情况。
- 整理后的笔记不写“保留原笔记”“原文有误”等迁移过程或新旧对照；必要的版本和验证边界直接说明。
- 笔记之间尽量不写交叉引用（Markdown 链接、wiki 链接）；目录调整时链接易失效，主题关联用正文说明或靠文件名检索即可。
- 不主动增加手写目录、批量脚本、教程附录或与当前主题无关的扩展内容。
- 标题最多三级。

### 文风与顺序

- 简明扼要：短句直说，一句一个意思；不用自造缩写、箭头链、口号和形容词堆砌；不写客套、过渡和总结句。
- 不用教学口吻：不写“所以要……”“我们来看”“你可能会问”、设问和白话类比。
- 按读者使用顺序组织：前提和参数先于操作，操作按执行顺序排列；先定义后使用，不提前引用后文才出现的对象。

### 操作与命令

- 先查询当前状态和前提，再给修改、验证及撤销方法。开启/关闭、自启/取消、定时/取消、限制/恢复等成对写出；区分“停止当前运行”与“阻止以后再次运行”。
- 命令保持完整，模板占位值明确标注。
- 除 `cd`、`ls`、`cat`、`cp`、`mkdir`、`rm`、`printf`、`reboot` 等基础命令外，每条命令在行尾加 `#` 注释写作用；管道和组合命令写整行目的，关键参数一并说明。不支持行尾注释的配置格式使用独立注释行。
- 命令一行一条，不用 `\` 续行，不把数组、管道拆成多行；过长时先赋值变量再引用。
- 配置文件内容写成“文件路径 + 内容代码块”，用编辑器写入，不用 heredoc。
- 模板写明文件位置、前置依赖、需替换的值和生效方式；占位模板不声称可直接运行。
- 区分查询与变更，标明中断服务、触发任务、挂载或安装等副作用。恢复以原状态为准，不把“取消限制”混同于“恢复原值”。
- 引用实际案例时区分历史记录与本次核实的状态；静态语法检查不能表述为已完成部署或业务验证；未经验证的结果标注为“预期”。

### 附件

默认结构：

```text
章节目录/
  笔记A.md
  笔记B.md
  assets/
    笔记A-slug/
    笔记B-slug/
```

- `foo.md` 的附件放在同目录 `assets/{笔记文件名-slug}/`。
- Markdown 图片使用相对路径：`![alt](assets/{slug}/file.png)`。
- 从外部平台迁移时下载远程图片和附件并替换链接。
- 单篇附件很多或包含画板源文件时，可使用 `笔记名/笔记名.md + assets/` 结构。
- 语雀画板或导图保留 `.lake`、`.lakecard` 源文件，并增加同目录 Markdown 说明，不强制转为纯 Markdown。

### Excalidraw

- 需作为独立画板编辑的架构图、拓扑图、关系图等默认使用 Excalidraw；笔记内的简短流程图使用 `text` 代码块。用户明确指定形式时遵从指定。
- 使用现代 Markdown 格式 `.excalidraw.md`，放入笔记对应的 `assets/{slug}/`。
- 正文使用 `![[assets/{slug}/{画板名}.excalidraw|宽度]]`，链接不得写成 `.excalidraw.md`。
- 保留插件生成的文件结构，不手工改写 `## Text Elements` 或压缩数据。
- 程序生成画板时使用 `excalidraw-plugin: raw`，文字写入 Drawing JSON。
- 交付前同时检查 Excalidraw 视图和笔记嵌入效果；仅验证 JSON 和文件存在不算完成。

### Markdown 与代码块

- 并列场景、阶段或操作路径需要分别写清条件和做法时，用编号列表逐项组织；不要把多种情况压进同一长段，也不要为普通叙述强行编号。
- 多步或分支流程适合图示时，用简短的 `text` 代码块画输入、关键步骤、分支与输出；简单过程不强制配图。
- 表格用于参数、数值、映射和便于横向比较的信息。
- 标题后、段落间、代码块和表格前后保留一个空行。
- 所有代码块标注语言；命令使用 `bash` 或 `shell`，输出使用 `text`。
- 围栏及块内命令从第一列开始，不保留迁移内容中的四空格缩进。
- Linter 负责 Markdown 结构，Prettier 负责整篇排版，Simple Code Formatter 只处理支持的单个代码块。
- `bash`、`shell`、`python`、`plsql` 等未配置自动格式化时，保持顶格并人工整理。

## 知识笔记

### 写法

- 用于回看原理、复习方法和实际操作，不写成工作流水账、临时排查过程或官方文档摘录。
- 用事实陈述写清“解决什么问题、为什么这样做、如何工作”，不用教学口吻；必要术语首次出现时给一句定义，避免用另一组术语解释术语。保留准确性，不用口号、拟人化比喻或冗长对话代替逻辑。
- 概念、方法和工具按各自特点独立说明，保留背景、做法、问题和用例；可用短条目组织，不强行填入统一栏目。
- 不用密集大表格代替概念解释；长段落按主题拆开，避免压缩后只剩抽象结论。
- 使用简短标签如“优点：”“问题：”“用例：”，不添加“问题也很直接”“好处是”“这说明”等无必要的阅读转折，也不靠冗长问答制造亲切感。
- 用户自己的部署和机器案例写入实践手册，不写进知识笔记。

### 结构

用户指定结构时严格遵循。同一主题的概念、规则和操作命令写在同一章节，不拆到“概念”“操作”两处。完整的工具或系统专题默认按以下顺序组织；短知识点按需合并，不为凑章节扩写：

1. **介绍与依赖**：做什么、解决什么问题，需要哪些软件包、服务或环境；区分系统已有、必需和可选依赖，先提供查询确认方法，再说明必要的安装操作。
2. **通用操作**：独立说明管理命令的作用、用法、参数和示例，不在每个子类型中重复解释同一套命令。
3. **核心概念与分类**：解释对象是什么、各类分别做什么、相互关系。说明参数值来自固定选项、系统已有对象还是用户自定义，并给出查询方式。
4. **分类详解**：逐类说明适用场景、工作逻辑、配置模板、参数含义和通用示例；不适用文件模板的类型，说明其真实创建方式。
5. **延伸阅读与边界**：需要时注明适用版本与尚未验证的范围；不依赖笔记间链接，外部官方文档可用完整 URL。

### 原理、代码与示例

- 参数说明交代实际效果，不只翻译名称；公式或代码块之后涉及多个符号、参数时，在块外用无序列表逐项解释，参数较多时使用表格。保留查询结果的判断依据。
- 实现类笔记建立原理与代码的对应：说明各脚本的职责、输入、输出、运行顺序和相关函数，并链接附件；代码注释解释关键算法约束与原因，不逐行复述代码。
- 多步算法用小示例讲清初始状态、关键步骤、状态变化、停止条件和最终产物，再说明新输入如何使用产物；不能只列统计方法或结果而省略中间机制。
- 区分处理中使用的状态、累计保存的数据和最终输出，明确哪些内容被替换、保留或新增，避免将局部变化描述为全部删除。

## 实践手册

- 只写：适用范围、参数、步骤、命令、通过条件、失败处置、回滚、验收表、维护动作、外部参考。
- 不写：原理解释、步骤顺序或做法的理由（“因为……所以……”“这条规则防的是……”）、背景故事、阅读指引、写作说明（“每一步只写……”“原理见……”）。
- 约束只写结论，如“前提：……”“不重启”“不执行 `upgrade`”，不附原因。
- 参数集中在开头的参数表；正文出现的占位值都在表中。
- 命令引用的值写成 shell 变量：参数表后说明“执行前在当前 shell 赋值，重连后重新赋值”；需在某步查询后才知道的值，在该步查询命令之后赋值。
- 每个变更步骤写通过条件；可能失败的步骤写失败处置；部署手册包含必要的停止、恢复和回滚步骤。
- 案例记录写日期、机器、现象、一句事实性原因、处置和结果，不展开原理。
- 流程图只用于总览步骤，图后不加解释。
- 交付前逐段检查，删除不能直接执行或判断的句子。
